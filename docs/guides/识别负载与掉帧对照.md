# 识别负载与掉帧对照

本版源码与 Windows 测试包包含以下识别调度。反馈中的掉帧原因尚未通过真实对局对照确认。

## 识别节奏

实时模式会根据所选区域的聊天活动调整节奏：

| 状态 | 截图与图像观察 | OCR |
| --- | --- | --- |
| 空闲且无已确认消息需要跟踪 | 最小周期 0.4 秒 | 约 1.2 秒一次保底检查，用户较慢配置继续有效 |
| 出现疑似新聊天或正文变化 | 最小周期 0.12 秒 | 最小周期 0.25 秒，或用户设定的较慢周期 |
| 活跃窗口结束、仍有已确认消息 | 保持 0.12 秒视觉检查 | 回到低频保底，原消息继续按视觉寿命显示 |

新聊天活动开启约 3.5 秒活跃窗口，后续新内容续期；稳定文字、位置小幅移动和仅有消息消失不会续期。一般游戏背景变化不会直接开启窗口，必须先出现可接受的疑似聊天正文。疑似活动只唤醒 OCR，原有候选检查、三帧投票、源图复核和过期截止仍然生效。

表中周期是调度下限，截图和识别实际耗时可能使处理更慢。0.4 秒探测用于争取把空闲首条新增等待控制在约 0.5 秒内；整条翻译耗时仍包含 OCR 与接口处理时间。

OCR 回退采用逐个按需读取，提前得到足够结果后不启动后续任务；避免同时启动四个回退 OCR。原生首选识别与源图复核仍使用现有单线程限制。聊天密集时同样受负载与截止约束，可能增加延迟或漏译，需结合实机结果评估。

配置一致的多语言串行回退现在复用常驻引擎，减少重复加载模型；英语短词的专用模型/字符配置仍走原兼容路径。引擎故障后关闭常驻进程，后续读取使用有超时保护的兼容路径。首页会在有效运行心跳中提示“识别加速暂不可用，正在使用兼容模式”。

“仅按快捷键识别”仍遵守已有请求窗口；未触发时没有 OCR。没有已确认身份需跟踪时，视觉探测也保持低频；按键后暂时提高采样。游戏不在前台或助手暂停时仍停止采集。

## 怎样验证改善

固定分辨率、显示模式、游戏画质、帧率限制和同一场景，分别比较关闭助手、优化前源码、当前源码。每种情况都观察安静时、聊天刚出现、连续聊天三段，并记录：

- 游戏平均帧率、帧时间尖峰，有条件再记录 1% 低帧。
- 助手及 OCR 子进程的 CPU 占用峰值与平均值。
- 第一条聊天从画面出现到显示译文的耗时，以及连续消息延迟。
- 画面中符合条件的消息总数、成功显示数、漏译原因；不能只数成功字幕。
- 原消息移动、换字、消失或切出游戏后，译文是否及时跟随和隐藏。

低频探测可能错过存在时间极短的消息。若游戏更流畅但漏译明显增多，应调整节奏并重新对照，不能单凭资源下降认定成功。相同截图的缓存、反复识别结果不能当成新的独立确认帧。

运行统计中的 `capture_adaptive_*` 是本次运行的累计计数：`idle`、`active`、`tracking` 表示视觉观察次数，`wakes` 表示从空闲进入活跃的次数，`ocr_started`、`ocr_skipped` 表示 OCR 调度机会。它们不等同于实际 OCR 子进程总调用数，也不能证明游戏帧率改善。
